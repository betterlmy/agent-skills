# 持久化与迁移规范

## 技术栈中立

- 先识别数据库类型、驱动、ORM/查询生成器、迁移工具、事务封装和连接池所有者。
- 沿用仓库已有的 `database/sql`、pgx、sqlc、GORM、Ent、Bun 或其他方案，不为统一风格引入第二套持久化技术。
- Repository、DAO、Store 或包级函数都不是普遍答案；选择应符合仓库依赖方向、事务边界和测试方式。

## 查询与连接

- 所有数据库调用传播 Context；设置合理的查询、事务和连接获取 Deadline。
- 参数使用驱动或库提供的绑定机制，不拼接不可信 SQL 标识符和值。
- 关闭 Rows 并检查迭代错误；区分未找到、冲突、取消、Deadline、瞬态错误和未知错误。
- 不默认启用全量 SQL Debug 日志；SQL 文本、参数和执行计划可能包含敏感信息或造成高开销。
- 分页必须有稳定排序和上限。大结果集使用游标、流式处理或批次，而不是无界加载到内存。

## 事务

- 事务边界由业务原子性决定，不由单个 DAO 函数机械决定。
- 同一事务中的调用必须显式使用事务句柄，避免部分操作意外落到连接池外。
- 所有退出路径回滚未提交事务，并检查 Commit 错误；不要在事务中执行不可控的长网络调用。
- 重试只用于确认安全且幂等的错误类别，并设置次数、退避、总 Deadline 和可观测性。

## Schema 与迁移

- 已发布或已应用迁移不可改写；Schema 变化新增迁移，并说明向前兼容、回滚和混合版本窗口。
- 大表 DDL、回填、索引创建、约束验证和类型变更必须评估锁、磁盘、复制延迟和部署顺序。
- 数据修复与结构迁移分开，批次有界且可恢复；不要假设事务能覆盖所有数据库 DDL。
- 外键、唯一约束、检查约束和非空约束优先在数据库保护数据正确性，同时保留应用层友好校验。
- 迁移测试只能连接明确可丢弃的独立测试库；执行会修改数据的命令前遵循仓库批准规则。

## 模型边界

- 领域对象不依赖 ORM 标签或数据库驱动类型，除非仓库明确采用 Active Record 风格。
- 时间、时区、金额、精度、JSON、UUID、枚举和空值语义必须在应用与数据库两侧一致。
- 软删除、审计字段、主键策略、表名前缀和索引命名是项目或组织决策，不是通用 Go 规则。
- 生成查询代码不手工修改；修改 Schema/Query 输入并运行固定生成器与漂移检查。

## 技术栈补充

- 使用 GORM 时继续读取 `gorm-database.md`。
- 编写或评审 SQL、DDL 和迁移时继续读取 `sql-standards.md`。
- 对版本敏感的驱动、ORM 和迁移行为，查阅仓库锁定版本的官方文档和源码。
