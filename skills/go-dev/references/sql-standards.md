# SQL 与数据库迁移规范

本文只提供跨数据库安全基线。具体语法、命名、目录、迁移工具和方言以目标仓库为准。

## 修改前

1. 确认数据库与版本、迁移工具、Schema 所有者、部署顺序和回滚策略。
2. 阅读当前完整 Schema、相关查询、约束、索引和相邻迁移，不只看 ORM Model。
3. 确认迁移是否已经发布或应用；已应用迁移不得改写，必须新增迁移。
4. 评估应用旧版本与新版本并存期间的兼容性。

## 通用规则

- SQL 标识符、占位符、布尔值、时间、JSON、UUID、自增和冲突语法必须符合目标方言。
- 查询值使用参数绑定，不拼接不可信输入；动态标识符使用闭集映射或驱动安全 API。
- 表、列、约束和索引命名遵循仓库现有规则，不强制 `t_`、`idx_`、`uk_` 或某种大小写。
- 主键、外键、唯一、非空和检查约束应表达真实数据不变量；考虑 `NULL` 对约束结果的影响。
- 索引服务于实际查询和约束，评估列顺序、选择性、覆盖范围、写放大和重复索引。
- 金额避免浮点类型；时间明确时区与精度；字符串长度、编码和排序规则按业务选择。
- 不使用 `SELECT *` 作为稳定应用契约；明确列顺序和扫描类型。

## 在线变更

- 新增可空列或带安全默认值的列，再分批回填，最后验证并收紧约束，是常见兼容路径；具体步骤取决于数据库能力。
- 大表索引、类型转换、列重写、外键验证和 `NOT NULL` 可能持锁或扫描全表，必须评估线上影响。
- 重命名或删除采用“扩展—迁移—收缩”，先让应用兼容新旧结构，再迁移数据，最后移除旧结构。
- 数据回填设置批次、顺序、暂停、重试、幂等和进度记录，不在一个无界事务中处理全部数据。
- DDL 是否事务化因数据库与语句而异；不要把应用事务经验直接套用到迁移。

## 数据变更

- `UPDATE`、`DELETE` 和回填必须有精确过滤条件，并在执行前估算影响行数。
- 数据修复脚本应可重复运行或有明确防重机制，并记录验证查询。
- 初始化数据是否使用 Upsert、版本表或普通 Insert 由仓库决定；不得覆盖用户可变配置。
- 生产数据变更需要备份、审计、审批或维护窗口时，遵循仓库和组织流程。

## 回滚与验证

- 回滚说明区分代码回滚、Schema 回滚和数据恢复；破坏性变更通常无法靠 Down Migration 完整恢复。
- 在可丢弃测试库验证 Up/Down 或前向修复路径、约束、索引和关键查询计划。
- 验证旧应用访问新 Schema、新应用访问过渡 Schema，以及部署中断后的恢复路径。
- 不在共享、开发、预发布或生产库运行会清表、回填或破坏数据的测试。

## 新建 MySQL 表时的推荐风格

仅当仓库没有命名和审计约定、且目标数据库明确为 MySQL 时，可采用以下默认偏好：

- InnoDB、`utf8mb4` 和明确的排序规则。
- 表和字段添加有业务意义的 Comment。
- 普通索引使用 `idx_`，唯一索引使用 `uk_`。
- 需要审计时使用创建时间、创建人、更新时间、更新人；是否软删除由业务决定。
- 时间精度、主键策略和表名前缀在项目级统一，但不假设所有表必须相同。

这些是推荐默认值，不得覆盖已有 Schema、其他数据库方言或仓库迁移规范。
