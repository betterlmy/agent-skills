# gRPC 与 Protobuf 规范

## 契约优先

- 先读取 `.proto`、生成配置、拦截器和相邻服务实现，确认仓库使用的 gRPC 与 Protobuf 版本。
- 不手工修改生成代码。修改 `.proto` 后运行仓库固定的生成、兼容性和漂移检查。
- 字段号一旦发布不得复用；删除字段时保留 `reserved`，避免重新解释历史数据。
- 新字段应具备可兼容的默认语义。需要区分未设置与零值时使用适合当前 Protobuf 版本的 presence 机制。

## 服务实现

- 服务结构体嵌入生成代码要求的 Unimplemented Server，并用编译期断言确认实现接口。
- 传播调用方 Context，尊重 Deadline 和取消；外部调用、重试和流处理必须有界。
- Unary 与 Streaming 的认证、授权、日志、指标和 Recovery 优先放在统一拦截器中。
- Stream 循环正确处理 `io.EOF`、Context 取消、半关闭、背压和单消息大小限制。

## 错误语义

- 传输失败、认证失败、限流、不可用、Deadline 和内部故障使用稳定的 gRPC Status Code，并避免泄露内部错误。
- 如果仓库契约已经用响应体 `code/message` 表示预期业务结果，可继续沿用；不要把系统故障伪装成成功响应。
- 仓库没有既有约定、且新建内部业务 RPC 时，推荐用响应体整数 `code/message` 表示预期业务结果，同时用 gRPC Status 表示传输、认证、限流、Deadline、不可用和未知系统故障；在 proto 注释和客户端文档中写清映射。
- 不依赖错误文本做客户端分支；需要结构化细节时使用稳定的错误详情消息。

## 可观测性与测试

- 在拦截器记录方法名、耗时、Status Code 和关联 ID，不打印完整 Protobuf 请求或响应。
- 对包含凭据、个人信息、Prompt、二进制内容和大集合的消息只记录白名单摘要。
- 使用 Buf 或仓库已有工具检查破坏性变更；补充跨版本、取消、Deadline、最大消息、流结束和错误映射测试。
- 真实网络集成、TLS、服务发现和代理行为需要单独的环境验证，不能由单元测试代替。
