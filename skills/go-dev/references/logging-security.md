# 日志、安全与可观测性

## 使用仓库日志入口

- 优先使用仓库已有日志封装和字段约定，不新增第二套日志器，也不绕过统一脱敏层。
- 仓库没有封装时，可选择标准库 `log/slog` 或项目明确采用的日志库；不要把任何私有包路径写成通用要求。
- 日志字段保持稳定、低基数并可查询。关联 ID 从 Context 或中间件传播，不在业务代码中重复生成。

## 禁止内容

不得记录或返回以下原始内容：

- Token、Cookie、密码、Secret、Authorization、私钥和连接凭据。
- 完整请求体、响应体、Header、Prompt、模型隐藏推理和上传文件。
- SQL 参数、个人敏感信息、未受控远端响应正文和内部堆栈。
- 带 Query 或 Fragment 的敏感 URL。

仅把字段名列入黑名单不足以保证安全；嵌套结构、错误链和格式化对象仍可能泄密。优先记录白名单元数据和摘要。

## 推荐风格

- 在 HTTP 中间件或 gRPC 拦截器统一记录入口、出口、耗时、结果分类和关联 ID，避免每个 Handler 重复打印 in/out 文本。
- 业务层记录有诊断价值的状态变化和外部操作结果，不记录“开始调用某函数”之类低价值噪声。
- 错误日志包含稳定错误类别和安全上下文；是否附加错误链取决于仓库脱敏能力。
- 对字符串、集合和错误链设置长度上限；高频路径考虑采样和日志等级。
- 不把日志成功当成业务成功，也不让日志失败改变核心业务结果，除非审计日志本身就是事务要求。

## 协议边界

- 客户端消息应稳定、可本地化且不含内部实现；不要使用 `err.Error()` 直接构造公开消息。
- 认证失败不提示凭据、账号或资源是否存在等额外信息。
- 对外 URL、重定向和下载名称必须校验，防止开放重定向、Header 注入和路径穿越。
- Panic Recovery 只作为最后保护，必须避免重复写响应，并让进程级致命错误按架构要求处理。
