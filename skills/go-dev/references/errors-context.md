# 错误、Context、资源与并发

## 错误语义

- 用 `%w` 包装需要保留因果关系的错误，例如 `fmt.Errorf("load task: %w", err)`。
- 用 `errors.Is`、`errors.As` 或稳定的类型/哨兵错误分类，不比较错误字符串。
- 每一层只增加该层有价值的上下文，避免重复包装出冗长且泄密的错误链。
- 公开边界把内部错误映射为稳定、有限的协议错误；未知错误使用通用消息，原始错误只进入受控日志。
- 不忽略事务提交、编码、写入、关闭等可能改变结果正确性的错误。确实只能尽力处理时，用注释或受控日志说明。

## Context

- `context.Context` 通常作为第一个参数，不存入长期存活的结构体，也不传 `nil`。
- 传播调用方 Context；只有进程生命周期、后台任务等真正独立的根操作才创建新的根 Context。
- 建立超时时先检查仓库或上游是否已有更严格 Deadline，避免每层随意叠加固定超时。
- 不把可选业务参数塞进 Context；Context Value 只承载跨调用边界的请求级元数据，并使用私有键类型。
- 循环、重试、阻塞发送和长计算必须能响应 `ctx.Done()`。

## 资源生命周期

- 获取资源后尽快安排释放；检查 `Close`、`Flush`、`Commit` 等对结果有影响的错误。
- HTTP 响应体、数据库 Rows 和文件必须关闭；读取前设置合理的大小与时间边界。
- 事务明确提交或回滚，回滚应能覆盖所有提前返回路径。
- Ticker、Timer、临时文件和子进程必须有停止或清理路径。

## 并发

- 并发数量、队列和重试必须有上限；不要为每个输入无条件启动 goroutine。
- 明确 goroutine 的所有者、退出条件、错误传播和关闭顺序。
- Channel 由发送方或拥有完整生命周期的一方关闭；接收方不要猜测关闭时机。
- 多错误并发优先使用仓库已有的 errgroup 或等价模式，并传播 Context 取消。
- 修改共享状态时选择消息传递、Mutex、原子操作或不可变快照之一，并用竞态测试验证关键路径。
- 不在持锁期间执行网络、磁盘或其他不可控阻塞操作。
