# AGENTS.md 内容模型

## 核心判断

只有同时满足以下条件的内容才适合写入：

1. 它会改变 Agent 的决策或执行方式；
2. 它适用于目标目录作用域；
3. 它来自仓库事实、适用上级指令或用户确认；
4. 它能被执行、观察或验收；
5. 它没有在上级文件中被充分说明。

不满足这些条件的背景信息应留在 README、架构文档或贡献指南中。

## 推荐章节

每个仓库级 `AGENTS.md` 必须先具备以下五个最低章节；其余章节应按项目实际选择，而不是全部生成。标题可使用等价中英文表达，但不能合并到无法分别定位的单一章节中：

1. 仓库定位：项目用途、边界和规则适用范围；
2. 技术栈：语言、框架、构建工具和关键运行时；
3. 目录结构：影响 Agent 定位和修改的关键目录；
4. 文档索引：开发相关文档及其路径；
5. Skill 索引：仓库内 Skill 或 Skill 入口及其路径。

文件总行数不得超过 240 行。超过上限时删除重复、背景性和不会改变 Agent 行为的内容。

### 作用域与优先级

仅在存在多级规则、Monorepo 或宿主特定语义时写。说明该文件适用的目录，以及与上级规则的关系；不得声称能覆盖系统或用户指令。

### 项目结构

只列 Agent 定位和修改代码所需的关键目录。不要复制完整目录树，也不要描述不会影响操作的业务背景。

### 工作流

写清修改前必须读取、检查或确认的事项。把需要用户批准的操作限定到明确场景，避免所有微小修改都被不必要阻塞。

### 项目特有编码规则

只记录无法从格式化器、Lint 配置或常规语言习惯直接推断的约束。规则应包含适用范围；能链接权威文档时，不复制长篇细节。

### 命令与验证

每条命令应包含：

- 精确命令；
- 执行目录；
- 用途或适用改动；
- 必要时说明前置条件和副作用。

区分最低验证、相关测试和完整验证。不要把未运行的命令表述成已验证。

### 修改边界

重点覆盖生成文件、数据库迁移、公开 API、依赖、密钥、发布和 Git 操作。禁令应说明边界，不要用无限扩张的“任何修改都必须先确认”。

### 同步维护与防漂移

这是强制内容，不因文档采用精简结构而省略。要求项目结构、技术栈、构建或测试命令、生成流程及开发约束变化时，在同一变更中更新对应作用域的 `AGENTS.md`。只更新实际受影响的指令文件，避免无关层级产生噪声变更。

推荐规则：

```markdown
如果项目结构、技术栈、构建或测试命令、生成流程、开发约束发生变化，必须在同一变更中同步更新适用作用域的 `AGENTS.md`，确保其中的目录、命令和约束与仓库现状一致。
```

### 完成标准

要求汇报实际改动、运行过的检查、未验证事项和剩余风险。完成前检查本次变更是否触发 `AGENTS.md` 同步更新。不要要求 Agent 声称所有测试通过，除非确实运行过。

### 最低结构与长度检查

审查或生成完成后，确认五个最低章节均存在，且 `AGENTS.md` 不超过 240 行。缺少任一章节或超过行数上限都属于未完成，不得只作为一般建议记录。

## 强弱规则示例

### 测试

弱：

```markdown
请适当运行相关测试。
```

强：

```markdown
修改 `internal/order/` 后，先在仓库根目录运行 `go test ./internal/order/...`；提交结果前再运行 `go test ./...`。若完整测试依赖外部服务，报告未运行原因。
```

### 生成文件

弱：

```markdown
不要修改生成文件。
```

强：

```markdown
不要直接编辑 `api/generated/`。修改 `api/openapi.yaml` 后，通过 `make generate-api` 重新生成，并检查生成差异。
```

### 高风险操作

弱：

```markdown
危险操作需要谨慎。
```

强：

```markdown
数据库迁移、依赖主版本升级和公开 API 删除必须先给出兼容性与回滚方案，并获得用户确认后执行。
```

### 目录描述

弱：

```markdown
`src/` 包含项目源代码。
```

强：

```markdown
共享协议定义位于 `src/contracts/`；修改后必须同步运行契约测试，不要在业务模块中复制协议类型。
```

## 最小版本

信息较少时，宁可生成短文件，也不要填充猜测。最小有效内容仍必须包含五个最低章节；无法可靠确认的项目事实应明确标注未知并询问用户，不得用猜测填充。除此之外，最小版本通常还需要：

1. 已确认的关键命令；
2. 明确的修改边界；
3. 防止项目事实与 `AGENTS.md` 漂移的同步维护规则；
4. 完成与汇报要求。

如果连这些内容也无法可靠确认，应先询问用户，而不是生成看似完整的模板。

## 删除检查

完成草稿后逐条询问：删除这条规则是否会改变 Agent 行为？如果不会，删除它。还应删除：

- “遵循最佳实践”等无验收标准的口号；
- 与上级文件重复的规则；
- 仅介绍产品而不影响开发的段落；
- 私有绝对路径、临时分支名和易过期版本信息；
- 无法追溯来源的团队偏好。
