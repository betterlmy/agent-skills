# 前向测试用例

## 应触发

1. “扫描这个仓库，找出可以删除的抽象、wrapper 和无用依赖，只给报告。”
   - 应采用 `standard` 整仓审计。
   - 应核验调用方、配置、测试和隐式注册。
   - 不应直接修改代码。
   - 应在回复中直接交付报告，不应默认创建临时文件。

2. “比较 repo-a、repo-b、repo-c 有哪些过度设计，按收益排序。”
   - 应逐仓独立建立证据，再汇总共同模式。
   - 不应仅因跨仓代码相似就建议合并。
   - 应在回复中按仓库分节并提供汇总；只有用户要求文件时才生成逐仓报告文件。

3. “快速看看这个老项目有没有手写标准库功能和单实现接口。”
   - 应采用 `quick`，明确结论不代表完整语义审计。
   - 默认应输出候选；只有局部证据闭合且未检查区域不会影响结论时，才可输出正式发现。

## 临界场景

1. “这个接口只有一个实现，把它删掉。”
   - 应先核验边界职责、测试替身、外部消费者和近期变化需求。
   - 证据不足时只能列为候选，不能直接确认删除。

2. “扫描生成目录里哪些文件最大。”
   - 不应触发；这是文件统计任务，不是过度工程审计。

3. “把扫描报告保存到仓库里。”
   - 应读取仓库文档约定；没有明确目录且写入会产生新文件时应先澄清。
   - 不应自行修改 `.gitignore` 或覆盖已有报告。

4. “按 standard 审计这个包含 300 个包的 monorepo，今天先给我能确认的结果。”
   - 应先统计规模并划分模块或批次。
   - 无法完整覆盖时应交付“部分覆盖”报告，列出已检查和未检查区域。
   - 不应把局部发现表述为完整整仓结论，也不应为了满足 `standard` 无限扫描。

5. “按 standard 审计这个库；仓库外可能有人调用公开接口，但目前没有消费者清单。”
   - 应闭合仓库内调用、配置、测试和契约证据。
   - 若仓库外消费者可能推翻删除或内联建议，应降级为候选。
   - 若建议仅精简内部实现且保持公开契约不变，可以保留中置信度正式发现，并明确仓库外未验证。

6. “报告必须估算能删除多少行，但现有证据只能确认可以合并一层内部包装。”
   - 不应虚构代码行数区间。
   - 应使用定性收益，并说明量化需要先形成具体改动方案。

## 不应触发

1. “审查这个 PR 是否有安全漏洞和并发错误。”
2. “定位接口的所有调用方，但不要评价设计。”
3. “直接重构这个模块，让测试通过。”

## 执行协议

每次发布前至少执行以下轻量前向评测，并把结果记录在 `results.md`：

1. 从“应触发”选择一个普通场景，从“临界场景”选择一个证据不足或大仓场景，从“不应触发”选择一个近邻任务；涉及深度规则变更时，额外覆盖 `quick` 与 `standard` 的结论门槛。
2. 对比修改前版本或无 Skill 基线，记录触发判断、执行范围、是否产生未授权写入、正式发现是否满足证据门槛。
3. 核心准确性评测至少使用一个包含真阳性和易误报路径的真实或合成仓库，覆盖直接调用、动态注册或反射、公开契约、测试专用实现和语义不同的相似代码；记录正式发现、候选降级、误报与漏报。
4. 记录实际观察、失败与限制；没有运行独立模型或真实仓库时必须明确说明，不得把静态检查或同一会话人工演练写成端到端评测。
5. 只有可泛化的失败才进入主流程，避免为单个用例硬编码规则。
