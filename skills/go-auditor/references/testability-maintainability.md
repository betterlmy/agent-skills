# 可测试性与可维护性（第三步）

从测试证据、依赖可替换性、可观测性和公开契约评估指定范围是否易于安全修改与故障排查。局部与 diff 审计读取所属 package 测试和直接契约，不据此评价未审计区域。

## 单元测试存在性与质量

- 核心业务（鉴权、Token、租户、支付、并发逻辑）是否有与风险匹配的测试：

  ```bash
  find . -name '*_test.go' -not -path '*/vendor/*' | head
  ```

- 只测"开心路径"（Happy Path）：缺少错误分支、边界、并发场景。
- 断言是否有效：`if err != nil { t.Fatal }` 之后是否真的校验了结果，还是仅"不 panic 即通过"。
- table test 覆盖：是否系统化覆盖输入矩阵。
- 测试是否依赖外部服务（真实 DB/Redis/网络）导致无法隔离运行；应 mock 或用 testcontainers。

## 可测试性设计

- 高度耦合外部服务：直接在 service 里 `NewClient()`、包级全局连接，无法注入 mock。
- 是否使用依赖注入（构造函数传 interface）；interface 是否窄到可 mock。
- 时间、随机、ID 生成是否硬编码（`time.Now()`、`rand.Intn`），导致测试不确定；应注入时钟/种子。

## 覆盖率与竞态纳入 CI

- 覆盖率阈值以仓库、团队或监管要求为准。没有明确阈值时报告分布和关键未覆盖路径，不自行发明统一及格线。
- `-race` 是否纳入 CI，还是只在本地偶尔跑。
- 覆盖率不等于质量：高覆盖但断言无效比低覆盖更危险，需读测试体确认。

## 日志与可观测性

- 日志级别混乱：Error 打正常流、Info 打噪音。
- 结构化缺失：`log.Printf` 字符串拼接而非 `slog`/`zap` 结构化字段。
- 缺关联 ID/traceID：跨服务调用无法串联。
- 关键路径是否有 metrics（耗时、错误率、业务计数）。
- OTel span 是否在 RPC/DB 边界传播。

## 错误码与公开契约

- 错误码是否集中定义，还是散落硬编码字符串/数字。
- 内部错误是否直接暴露给调用方（泄露实现）；应映射为对外错误码 + 内部日志。
- gRPC proto 错误码与 HTTP 网关映射是否一致。

## proto / API 兼容（gRPC 微服务）

- 删除字段、改变字段类型或复用字段编号是兼容性高风险候选；结合是否已发布、保留字段和消费方证据判断是否达到阻断级。
- proto 定义与实现是否漂移：proto 有方法但 service 未实现，或反之。
- 共享 proto（如独立 `xxx_shared` 仓库）变更是否同步到所有消费方。
- 枚举值新增是否影响既有 switch 分支（未加 default 静默漏处理）。

## 文档与注释

- 注释是否解释"为什么"（业务背景、特殊 hack、约束），而非机械复述"做了什么"（`// 赋值 a 为 1`）。
- 导出标识符是否有一句话注释。
- `README`、交接文档、`docs/` 是否与代码现状一致（命令、端口、依赖是否过期）。

## 产出

- 测试缺口：无测试的核心包、仅开心路径、断言无效、不可隔离。
- 可测试性障碍：全局耦合、硬编码时间/随机。
- 可观测性缺口：级别混乱、缺 traceID/metrics。
- 契约风险：错误码散落、proto 破坏性变更、文档漂移。
