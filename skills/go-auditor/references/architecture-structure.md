# 宏观架构与工程规范（第一步）

先用目录、模块和包依赖建立与审计范围匹配的结构视图，再按风险读取必要源码。只有 `repo`/`module` 范围做完整结构画像；package、目录、文件和 diff 范围只建立所属层次及直接依赖上下文。命令示例中的 `.` 仅适用于整仓或模块，局部审计必须替换为实际路径或 package 范围。

## 项目结构与模块划分

- 识别 `cmd/`、`internal/`、`pkg/` 等目录承担的真实职责。缺少某种目录并不自动构成问题；库、小型工具和多模块仓库可能采用不同布局。
- 检测"万能包"：单目录文件数过多、单文件超长。命令：

  ```bash
  find . -name '*.go' -not -path '*/vendor/*' -exec wc -l {} + | sort -rn | head -20
  ```

  大文件仅作为候选。结合职责数量、变更频率、依赖数量和测试困难度确认是否属于 god file。

- 包名与目录名是否一致；是否有 `util`/`common`/`helper`/`misc` 黑洞包（什么都往里塞）。

## 依赖方向与循环依赖

- Go 编译器本身禁止包级循环依赖，但模块/层间逻辑循环仍可能存在（A 调 B，B 反向调 A 的接口）。
- 分层是否倒置：例如 handler 调用 service、service 调用 dao 的预期方向是否被打破。检查 dao 反向依赖 handler、service 依赖传输层对象等候选，但先确认项目实际架构约定。
- 用 `go list -f '{{.ImportPath}} {{join .Imports " "}}' ./...` 展开包级依赖。定义、调用关系和影响分析优先使用宿主已提供的语义索引或代码图工具；不可用时用 `rg` 发现定义、注册点与入口候选，再读取源码和测试交叉验证。文本命中不能单独证明调用关系。

## 全局状态与副作用

检测包级可变全局变量与 `init()` 副作用，它们破坏可测试性、隐藏依赖：

```bash
rg -n '^var\s+(\(|[A-Za-z_][A-Za-z0-9_]*)' --type go -g '!*_test.go'
rg -n '^func init\(\)' --type go
```

- 包级可变全局可能隐藏依赖；结合生命周期、并发访问和测试替换需求判断是否应改为构造函数注入或其他所有权模型。
- `init()` 里做 RPC、DB 或文件 IO 是高风险候选，需结合失败处理、可测试性和启动影响判断严重度。

## 命名与风格一致性

- 缩写是否统一：`ID`/`URL`/`HTTP`/`API` 而非 `Id`/`Url`/`Http`。
- 接口命名：单方法接口是否 `er` 后缀；大接口是否违反 ISP（方法数过多）。
- `any`/空接口泛滥检测：

  ```bash
  rg -n 'interface\s*\{\s*\}|^type\s+\w+\s+interface' --type go
  ```

## 工程配置（repo/module 范围）

- `.golangci.yml` 是否存在且启用了关键 linter（见 tooling-baseline.md）。
- `.gitignore` 是否漏忽略构建产物、本地配置、覆盖率文件和证书。
- `Makefile` 命令是否与真实构建/测试一致；CI 是否真的执行 lint 与 race。
- `go.mod`：Go 版本、`replace` 滥用、间接依赖失控。

## 产出

- 与审计范围匹配的依赖上下文与违反方向点。
- 仅在相应范围内给出 god package / god file 候选（附行数）。
- 全局状态与 `init()` 副作用清单。
- 工程配置缺口（lint/CI/gitignore）。
