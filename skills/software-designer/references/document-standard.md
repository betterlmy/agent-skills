# 软件设计文档标准

## 1. 目标

软件设计文档应让读者能回答以下问题：

- 为什么建设，解决什么问题，哪些内容不在范围内；
- 系统由什么组成，组件如何依赖，关键决策为何这样选择；
- 核心业务如何流转，正常与失败路径如何处理；
- 数据、接口、一致性、安全和权限边界是什么；
- 如何部署、观测、验证、迁移和回滚；
- 哪些是事实、设计决策、推断或仍待确认的事项。

文档的评价标准是“能指导实现、评审和验收”，不是章节数量。

## 2. 深度选择

| 深度 | 适用场景 | 建议内容 | 图表 |
| --- | --- | --- | --- |
| 简版 | 单模块、小功能、低风险变更 | 背景范围、方案、流程、数据/API、风险、验证 | 1～2 张 |
| 标准版 | 新系统、跨模块功能、正式技术设计 | 完整核心结构 | 2～5 张 |
| 详细版 | 高风险、强合规、高并发、复杂迁移 | 状态、异常、容量、灾备、迁移等专项设计 | 按视角拆分 |

默认采用标准版。某章节没有影响实现或验收的信息时可合并或删除，不要保留“暂无”占位。

## 3. 标准结构

### 3.1 文档信息

至少记录标题、版本、状态、日期、作者或责任角色、目标读者和修订记录。需要说明设计事实来源时使用“形成方式”和“事实基准”，不要把它写成系统设计模式。示例文档可以标明“示例”，避免被误认为正式基线。

### 3.2 背景、目标与范围

- 背景描述系统或功能为什么存在、原有问题及其业务或技术定位；
- 目标描述需要达成的能力和可验证结果；
- 列出范围内、范围外和外部依赖；
- 定义关键术语、假设和硬约束；
- 避免把解决方案提前写进需求目标。

需求驱动、代码逆向和增量维护只是形成方式，不改变本节语义。不得用“分析代码”“还原当前实现”“生成文档”替代系统背景、建设目标或责任范围；目的证据不足时使用中性表述，并将推测标为“推断”或“待确认”。

### 3.3 需求与质量属性摘要

只保留会影响设计的需求。为核心需求分配稳定编号，例如 `FR-01`、`NFR-01`。质量属性必须可验证，不能只写“高性能”“高可用”。未确认的容量、延迟和 SLA 要明确标记为目标假设。

### 3.4 系统上下文与总体架构

应说明：

- 用户、外部系统、信任边界和数据流；
- 组件职责、依赖方向、同步与异步交互；
- 数据事实源、缓存和派生数据的定位；
- 影响较大的技术决策、备选方案和取舍。

架构图展示稳定边界，不要把所有类、表或云产品堆到一张图中。

### 3.5 模块设计

每个核心模块建议说明：

| 项目 | 内容 |
| --- | --- |
| 职责 | 模块拥有的业务能力和数据 |
| 输入/输出 | 命令、查询、事件或接口 |
| 依赖 | 允许依赖的模块和外部服务 |
| 规则 | 不变量、状态、权限、幂等和事务边界 |
| 失败处理 | 可预期异常、重试、补偿和降级 |

辅助模块使用一行摘要即可。不要把源码目录树改写成模块设计。

### 3.6 核心流程

选择 1～3 个决定系统正确性的流程。每个流程包含：前置条件、触发者、主路径、关键失败路径、事务或一致性边界、结果和审计要求。跨组件交互优先使用时序图；生命周期优先使用状态图。

### 3.7 数据设计

- E-R 图只展示核心实体和真实基数；
- 数据字典突出主键、业务唯一键、外键、状态、版本和敏感字段；
- 说明索引目的、事务边界、删除策略、历史版本和数据保留；
- 区分事实表、主数据、缓存、搜索索引和报表副本；
- 对逆向文档，数据库迁移或 Schema 的证据优先于对象名称推测。

### 3.8 API 与外部集成

接口清单应包含方法或消息、路径或主题、用途、调用方、鉴权和关键错误。只为核心接口给出请求响应示例。统一说明版本、分页、幂等、错误、时间、并发版本和追踪约定。

外部集成需说明协议、数据方向、认证、超时、重试、幂等、失败降级和责任边界。

### 3.9 非功能设计

仅写可落地、可验证的内容：

- 性能与容量：负载模型、分位延迟、吞吐、热点和压测方法；
- 安全与隐私：身份、授权、数据范围、加密、脱敏、审计和威胁控制；
- 可用性与韧性：超时、重试、熔断、降级、RPO 和 RTO；
- 可观测性：日志、指标、链路、业务指标和告警；
- 兼容性：接口、数据、客户端和部署兼容边界。

若输入没有给出数值，不得虚构为已确认指标。可以给出“建议目标”，但必须说明需要谁确认。

### 3.10 部署、发布与迁移

说明运行单元、网络边界、数据服务、环境差异、配置与密钥、健康检查、发布策略和回滚条件。涉及旧数据或不兼容 Schema 时，补充映射、试迁移、校验、切换和恢复方案。

### 3.11 测试与验收

从设计风险反推测试，而不是只列测试类型。至少覆盖权限越界、并发冲突、状态边界、事务回滚、依赖故障、数据迁移和核心性能目标中适用的部分。

### 3.12 决策、风险与追踪

- 关键决策记录“决策、理由、替代方案、后果、复审条件”；
- 风险记录“可能性、影响、缓解措施和责任角色”；
- 待确认项记录“问题、影响、负责人和截止条件”；
- 追踪矩阵连接“需求/用例 -> 模块 -> 数据/API -> 测试”。

## 4. Mermaid 图表约定

- 使用稳定、语义清楚的英文 ID 和面向读者的中文标签；
- 同一对象在不同图和正文中使用同一名称；
- 架构图通常不超过 12 个主要节点，复杂系统按上下文、容器、组件分图；
- E-R 图省略普通审计字段，保留主键、外键、唯一键和关键状态；
- 时序图使用 `alt`、`opt`、`loop` 展示确有价值的分支，不复制每个函数调用；
- 图中不承载唯一事实，正文必须解释边界、规则和例外；
- 本地没有渲染器时，至少检查图类型声明、成对围栏、参与者和引用 ID。

## 5. 事实与措辞

| 状态 | 使用条件 | 推荐措辞 |
| --- | --- | --- |
| 已确认 | 有需求、代码、配置、Schema、测试或运行证据 | “系统通过……”“配置定义……” |
| 推断 | 多项证据支持但没有直接声明 | “推断为……，依据是……” |
| 待确认 | 证据缺失且影响设计 | “待确认：……；影响……” |
| 建议 | 面向目标设计的方案 | “建议采用……；理由……；代价……” |

不要使用“显然”“应该是”“大概”等无法审计的表达。

事实状态是准确性标记，不是正文结构。有充分证据的普通设计事实可以直接陈述；推断、建议和待确认必须显式标记。测试代码存在与测试在本次任务中实际执行通过是两种不同证据，文档和完成报告不得混淆。

## 6. 完成质量检查

- 标题层级、表格、代码围栏、相对链接和 Mermaid 块完整；
- 范围外内容没有被悄然设计成系统责任；
- 模块、实体、接口、事件和状态命名一致；
- 每个核心流程包含失败路径和权限或一致性考虑；
- 关键结论可追踪到输入证据或明确标为建议；
- 没有凭空指定产品、版本、SLA、容量或部署环境；
- 文档不存在大段重复、源码逐行翻译或无信息的模板章节；
- 待确认项足以让后续负责人做出具体决策。
