# 从代码逆向软件设计文档

## 1. 目标与边界

代码逆向是一种设计取证方式。输出仍是一份正常的软件设计文档，背景、目标、范围、架构、流程和质量属性都描述系统或功能本身；形成方式只改变证据来源、事实状态和可追踪性要求。

代码逆向恢复“系统当前如何设计和实现”，不是替系统补写理想架构，也不是把分析过程写成设计正文。不得把“分析代码”“还原当前实现”“生成文档”当作系统背景、建设目标或责任范围。形成方式只需记录在文档信息、修订记录或设计依据中。

默认只读分析代码和运行资料；除非用户明确要求，不修改业务代码、配置、数据库或部署状态。

当用户还要求提出改进方案时，文档必须分成：

- **现状设计（As-Is）**：只记录有证据支持的当前实现；
- **目标设计（To-Be）**：记录建议、取舍、迁移步骤和风险。

只有同时交付现状和目标方案时才需要 As-Is/To-Be 结构；单纯代码逆向不应因此改变标准设计文档的章节语义。

## 2. 识别系统背景与建设目标

先从以下证据归纳系统为什么存在，再写背景和目标：

1. 用户、调用方和外部参与者；
2. 公开入口提供的核心用例；
3. 核心领域对象及其生命周期；
4. 系统集中维护的业务规则、状态和事实；
5. 外部系统之间由本系统承担的协调职责；
6. 安全、一致性、审计、合规和运行边界；
7. README、ADR、需求或产品文档明确声明的建设意图。

背景应说明原有问题、系统定位以及为什么相关职责需要由该系统承担。目标应使用能力和结果表达，例如“提供统一任务入口”“保证异步状态一致性”，不要使用“梳理入口”“追踪调用链”“还原数据库结构”等分析动作。

如果只能确认系统做了什么，不能可靠确认为什么建设：

- 将已确认能力直接写入架构和模块章节；
- 背景使用有证据支持的中性表述；
- 由多项证据归纳的动机标记为“推断”并说明依据；
- 会影响设计评审的目的缺口列为“待确认”；
- 不得用文档编写或代码分析目的填补系统建设目的。

系统范围描述设计对象承担和不承担的职责，不描述本次读取了哪些目录、文件或证据。取证范围和未验证边界放在设计依据或交付说明中。

## 3. 证据优先级

按以下顺序建立证据清单，但相互冲突时不要机械地认为文档一定高于代码：

1. 当前目录生效的协作指令、构建文件和项目文档；
2. 依赖清单、应用入口、模块边界和构建配置；
3. 路由、控制器、消息消费者、定时任务和公开接口定义；
4. 应用服务、领域模型、状态与关键业务规则；
5. 数据库迁移、Schema、模型映射、查询和事务代码；
6. 身份、外部客户端、消息、文件和其他集成适配器；
7. 运行配置、容器、编排、发布和监控文件；
8. 单元、集成、契约和端到端测试；
9. 可安全取得的运行证据，例如现有测试结果或只读健康信息。

README 表达意图，源码与配置表达实现，测试表达被验证的行为。三者不一致时记录差异，不擅自选择对用户最有利的结论。

## 4. 探索顺序

### 4.1 仓库定向

- 查看工作区状态，识别已有修改和生成文件；
- 使用文件清单了解顶层结构，读取构建文件和依赖清单；
- 查找更深层的协作指令并确认作用域；
- 识别单仓、多模块、单体、多服务、前后端分离或基础设施仓库形态。

优先使用快速文件和文本检索。环境提供语义符号、调用关系或影响分析工具时，可用于定位，但结论仍要回读源码和测试确认。

### 4.2 建立系统地图

先回答以下问题，再开始写正文：

| 视角 | 要找的证据 |
| --- | --- |
| 入口 | Web/CLI/Worker 启动点、路由注册、消息或定时入口 |
| 模块 | 包、项目、工作区、依赖方向、共享库 |
| 业务 | 核心实体、用例、状态、校验、事务边界 |
| 数据 | 迁移、表、索引、缓存、对象存储、搜索或报表副本 |
| 接口 | HTTP、RPC、消息、文件、批处理和回调 |
| 安全 | 认证、授权、数据范围、密钥来源、审计 |
| 运行 | 配置、部署单元、端口、健康检查、监控与告警 |
| 验证 | 测试如何证明关键行为，哪些路径没有覆盖 |

对大型仓库先确定系统边界和 1～3 个核心流程，再深入追踪；不要无目标地读取全部文件。

### 4.3 追踪核心流程

对每个核心流程，从入口向下追踪：

1. 触发者与协议入口；
2. 身份、权限和输入校验；
3. 用例编排与领域规则；
4. 事务开始、提交、回滚和并发控制；
5. 数据读写与外部调用；
6. 事件、异步任务、重试和补偿；
7. 返回值、错误映射、日志和指标；
8. 对应测试及未覆盖分支。

时序图应表达上述边界，不要逐行复制内部函数调用。

## 5. 证据记录

使用仓库相对路径和实际行号，例如 `src/order/service.go:87`。行号可能随代码变化，完成文档前重新核对。建议维护一张简短证据表：

| 结论 | 状态 | 证据 | 备注 |
| --- | --- | --- | --- |
| 订单写入与库存扣减同事务 | 已确认 | `src/order/service.go:87` | 事务由应用服务开启 |
| 通知失败不回滚订单 | 推断 | `src/order/service.go:112`、相关测试 | 未找到明确架构说明 |
| 生产是否使用只读副本 | 待确认 | 未找到生产配置 | 影响报表架构图 |

不要引用未读取的文件，不要生成不存在的路径或行号。

证据表宜集中放在设计依据或附录，不要让逐条“已确认”标记淹没正文。有充分证据的普通设计事实可以直接陈述；推断、建议和待确认必须显式标记。测试文件存在只证明有测试证据，只有本次实际执行成功才能写测试通过。

## 6. 常见推断陷阱

- 目录名为 `domain` 不代表实现了领域驱动设计；
- 定义了接口不代表运行时存在多个实现；
- 有缓存客户端依赖不代表核心路径启用了缓存；
- ORM 模型不一定等于生产 Schema，应继续核对迁移；
- 声明了消息生产者不代表事件可靠投递，应检查事务和重试；
- 配置样例不等于生产值，不得据此断言容量、拓扑或安全策略；
- 单元测试通过不代表集成和部署行为已经验证；
- 未找到实现不等于功能不存在，可能由生成代码、外部模块或运行时注册提供。

## 7. 已知限制与风险

发现文档、代码、配置和测试不一致时，单列“已知限制与风险”：

| 差异 | 证据 | 影响 | 建议确认人 |
| --- | --- | --- | --- |
| 文档称接口需要管理员权限，路由只校验登录 | 文档位置与路由位置 | 可能越权 | 模块负责人、安全负责人 |

只有用户授权修改时才实施修复；逆向任务本身只记录事实和影响。

## 8. 安全执行边界

- 读取源码、配置样例和现有测试属于常规取证；
- 不输出密钥、令牌、连接串密码或个人敏感数据；
- 不为取证启动生产服务、执行写数据库命令或调用有副作用的外部接口；
- 不自动安装依赖、初始化索引或运行生成器；这些操作有副作用时先取得授权；
- 运行测试前确认仓库约定和命令副作用，准确报告未运行或失败的检查。

## 9. 完成条件

- 背景、目标和范围描述系统本身，没有被逆向任务或取证范围替代；
- 架构图中的组件均有代码、配置或部署证据；
- 核心 E-R 关系由迁移、Schema 或明确映射支持；
- 核心时序覆盖入口、授权、事务、外部交互和关键失败路径；
- 现状、推断、建议和待确认项清楚分离；
- 关键结论具有可定位的证据，且没有把测试替身当成生产依赖；
- 测试存在与本次测试执行结果清楚分离；
- 明确列出未能验证的运行时注册、生产配置、外部系统或动态行为。
